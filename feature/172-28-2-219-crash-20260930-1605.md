## 3. 根因（Fiber 子模块，pin 270035b）

`~Http2SendAwaiter` → `cleanup(true)` 的隐含假设——**armed 的发送总能同步收回、hook 已回 Idle**——不成立：

1. `Http2Connection::cancel_queued_stream_send`（`src/http/Http2Connection.cpp:2164`）只同步回收三种状态：ConnectionWindow 等待、StreamWindow 等待、Queued（未编码进传输层）；**`State::InFlight` 返回 false**——批次已交给 socket 写路径，收不回来，完结只能等 wire 写完异步送达。
2. `cleanup(true)`（`include/fiber/http/detail/Http2SendAwaiter.h`）对返回值 `(void)` 无视，无条件 `owner_->stream().disarm_outbound(this)` → `Http2Stream.cpp:190` 断言 `state_ == Idle` 失败 → abort。
3. **更宽的窗口**：`ServerHttp2Request::cancel_queued_send`（`src/http/ServerHttp2Request.cpp:527`）开头 `if (abort_reason_ != IoErr::None) return false;` —— 客户端已 RST/流已 abort 时**连 Queued 状态都不收**，销毁同样必炸。
4. `Http2Connection::cancel_stream_send`（:2213，stream 关闭路径）对 InFlight 也只是标 `completion_result_`，不驱动同步完结——所有路径下 InFlight 的 Idle 回收都是异步的。
5. 对照：`on_timeout`（Http2SendAwaiter.h）对"取消不了"的处理是**正确的**——`cancel_queued_send()` 返回 false 时不 complete，继续挂起等在途写排空。唯独析构路径没有"继续等"的选项。这是 API 设计缺口，不是单处笔误。

### 修复方向（上游二选一 + 顺带项）

- **A. tombstone 移交**：`cleanup(true)` 时若 hook 非 Idle，不 disarm；把 `outbound_operation_` 的 ctx 从 awaiter 换成 stream/request 级存活的 tombstone（`on_encode`/`on_send_done` 回调不得再触已死协程帧），等异步 send_done 到达后自然清理。
- **B. conn 级同步 abandon**：提供强制回收 InFlight hook 的 API（写路径本就持有 encoded buffer，可安全放弃并回滚流量窗口），供析构路径调用。
- **顺带修**：`cancel_queued_send` 在流已 abort 时对 Queued hook 的滞留（上述第 3 点）。

按约定 Fiber 修复由用户亲自上游提交（`native/patches/` 仅作临时兼容补丁位）。

## 4. 触发场景与流量画像

- 崩溃流本身死在管道中间，**没有 access log 行**（LogWorker 异步、请求未完结不落行）。
- 16:05:03~16:05:08 邻域全部是 `ai-gateway.haierxj.cn/v1/messages`（`fiber-ai-server`，上游 172.28.2.113/.120，响应体 2~4 KB 流式、耗时数百 ms 级）；在途流极可能即是一条 `/v1/messages` 流式响应写 h2 客户端。
- 取消源（从 `execute [resume]` 由 WaitAwaiter 唤醒看）为 executor 等待的一方先就绪/取消：客户端断开（abort 回调）、上游读结束/出错、或 body 空闲计时器（84027c2 当天 14:07 才上线，但静默超时触发时写在途概率低——静默意味着本侧也少有新写；客户端 RST 撞在途写是更贴切的画像）。
- 概率画像：需要 客户端 h2（本机占比仅 4%，h1 60%/h3 36%）× 流式管道 × 取消恰逢写批次 InFlight —— 低概率、非确定性，**会重复发生**。
